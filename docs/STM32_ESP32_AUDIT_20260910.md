# STM32 ↔ ESP32 검사 기록 (2026-09-10)

## 결론

현재 STM32는 ST-Link 가상 COM의 USART2로 RPM/TPS 로그를 내보내지만,
PA9/PA10 USART1은 비활성이다. 기존 PA9 → ESP GPIO18 배선으로는 데이터를 받을 수 없다.
ESP 수신 소스의 긴 줄 처리와 카운터 문제를 수정했다. 첫 수정본 적용 후 부팅을 확인했으나,
최종 JSON 버퍼 보완본 업로드 도중 ESP USB 장치가 사라져 중단됐다.
**이후 USB 재연결을 확인하고 115200 baud로 최종 앱을 다시 업로드해 해시 검증과 부팅까지 복구 완료했다.**
STM32는 원본 펌웨어를 유지했다. 두 보드 사이 실수신 성공을 확인한 상태는 아니다.

## 장치 및 읽기 결과

| 항목 | 확인 결과 |
|---|---|
| STM32 | COM13, ST-Link, 디바이스 ID 레지스터 `0x10006421` |
| Flash 용량 레지스터 | `0x0200`, 512 KiB |
| USART1 BRR / CR1 / CR2 / CR3 | 모두 `0x00000000` |
| GPIOA MODER / AFRH | `0xaa800faa` / `0x00099000` |
| ESP32-S3 | COM8, CP210x, 업로드 도구에서 ESP32-S3 확인 |
| UART 통신 속도 | 115200, 8N1 |

COM13 실제 수신 예:

```text
L=0 R=0 cap=0/0 glt=0/0 tps=0 pct=0 idle=868
```

로그가 수신된 것과 Front 센서가 정상인 것은 별개이다.
현재 `tps=0`이므로 TPS/Front 통신까지 정상이라고 판단하지 않았다.

## 원본 추출 및 비교

- 원본: `.local/stm32-audit-20260910/stm32_flash_original.bin`
- 범위: `0x08000000`부터 524,288바이트.
- SHA-256: `8FCC7F1F9B0929DE16E4B9A8629D530B225FEE3263AD62B9545E53B0C6B74E31`
- 최초 SP `0x20020000`, Reset 벡터 `0x08004a15`.
- 마지막 비-FF 바이트 다음 오프셋: 53,024. 이것은 정확한 코드 크기 추정치가 아니다.
- 기존 `DJY_TQV/firmware/rear/Release/stm_rear.bin` 39,912바이트와 비교: 플래시 앞부분 불일치.
- 기존 Front 바이너리 18,008바이트와도 불일치.
- 플래시에 기존 `L=...idle=...` 형식 문자열이 존재하며 실제 로그와 일치한다.
- 저장소 커밋 `ee9d295...`에도 같은 문자열이 있으나, 같은 문자열만으로 펌웨어 동일성을 증명할 수 없다.
- 작업 중 STM에 halt/reset/erase/program 명령을 실행하지 않았다. 읽기 보호 해제도 하지 않았다.

바이너리는 C의 변수명, 주석, 원래 프로젝트 구조를 보존하지 않는다.
이 작업에서 원본 C 소스를 완전하게 역복원했다고 주장하지 않는다.
백업과 생성 바이너리는 `.local/`에 저장해 Git 업로드 대상에서 제외한다.

## 저장한 수정 사항

1. `firmware/esp32_ev_gateway/include/rear_uart_line.h`
   - 줄 버퍼를 기존 160바이트에서 512바이트로 확장.
   - 오버플로/NUL이 발생한 줄은 개행까지 버리고 다음 정상 줄부터 복구.
2. `firmware/esp32_ev_gateway/src/main.cpp`
   - 유효 RPM/TPS 로그마다 ESP의 `rear_uart_rx` 증가.
   - STM의 명령 수신 카운터는 `rear_command_rx/errors`로 분리.
   - 값 범위를 벗어난 기본 메시지를 거부하고 수신 오류 카운터에 반영.
   - 기본형 로그에서 없는 확장 상태의 freshness를 해제.
   - 확장 제어 상태를 최근에 받은 경우에만 UART 제어 전달/가능 표시를 허용.
   - STM 수신이 끊기면 IMU 정상 표시도 해제.
   - JSON 생성/릴레이 버퍼를 모두 2048바이트로 맞추고 잘린 JSON은 전송하지 않음.
3. `firmware/stm32_rear_uart/`
   - 고정 기준 커밋에 PA9 송신 전용 UART만 추가한 후보 소스.
   - 보드 원본에서 복원한 코드가 아니며 STM에는 미적용.
4. `scripts/build_stm32_rear_uart.ps1`
   - 기준 커밋 소스와 수정본을 EV 저장소의 `.local/` 아래에서 재현 빌드.
   - 원래 `DJY_TQV` 작업본과 사용자 변경을 수정하지 않음.
5. `tests/test_rear_uart.py`
   - 실제 ESP 파서와 줄 조립기를 호스트에서 컴파일해 검증.

## 검증 및 보드 적용 경계

- Python 테스트 30개 통과. 기본/확장 메시지, 160바이트 초과 메시지,
  수신/명령 카운터 분리, 범위 오류, 오버플로 뒤 복구, NUL 폐기 확인.
- ESP 최종 PlatformIO 빌드 성공: RAM 48,948바이트, Flash 905,221바이트.
- 첫 수정본은 COM8 업로드/해시 검증/부팅 확인 성공. 기존 로컬 Wi-Fi/릴레이 설정 유지.
- 첫 수정본 적용 후 실제 ESP JSON: `rear_uart_rx=0`, `rear_uart_errors=0`,
  `rear_command_rx=0`, `uart_ok=false`, `stm_online=false`, `live_control_allowed=false`.
- 같은 시점 Wi-Fi는 연결됨. 릴레이 HTTP 307, 전송 성공 카운터 0이므로 인터넷 피트 전달은 검증되지 않음.
  이것은 STM UART 미송신과 별도의 점검 사항이다.
- 이후 최종 JSON 버퍼 보완본 업로드는 USB 연결 소실로 실패.
  재시도 중 `OSError(22, 없는 장치를 지정했습니다., 433)` 발생.
  이후 포트 재조회에서 COM13 STM만 존재하고 COM8 ESP는 사라짐.
  COM8 재등장 후 esptool 115200 baud로 `0x10000`에 최종 앱 전체를 재기록했다.
  905,584바이트 쓰기 및 해시 검증 성공. 앞서 검증 완료한 bootloader/partition은 유지.
  재부팅 후 JSON 3개(seq 99~101)를 확인: Wi-Fi 연결, UART 수신 0, STM offline,
  live control 불가, HTTP 307. 최종 ESP 복구 완료이며 STM 실수신/피트 릴레이 성공은 여전히 미확인.
- STM 후보 ARM 컴파일/링크 성공: text 38,608 / data 160 / bss 7,544바이트.
  기준 HAL/FatFs/기존 소스의 경고는 존재한다. 무경고 빌드라고 판단하지 않는다.
  후보 BIN 38,780바이트, SHA-256 `B7667452B20D71B86BBFAA074643B8251224F585A04F1BA700EFCB058D6287F3`.
- STM 후보 플래시, PA9의 실제 파형, ESP 실수신, 센서/제어/차량 주행 검증은 수행하지 않음.

## 다음 결정

현재 STM 원본을 그대로 유지할지, 저장소 기준 제어 펌웨어로 교체할지 결정이 필요하다.
원본 유지 시 기존 USART2 PA2 TX를 이용하는 단방향 배선 대안이 있다.
PA9를 유지하려면 원본 소스에 UART 모듈을 추가하거나 준비한 STM 후보로 교체해야 한다.
자세한 범위는 [STM 후보 설명](../firmware/stm32_rear_uart/README.md)을 참고한다.

## 2026-09-11 재검사: 다른 팀 펌웨어

- 같은 ST-LINK 장치에서 코어를 halt/reset하지 않고 플래시 512 KiB를 다시 읽었다.
- 새 백업: `.local/stm32-audit-20260910/stm32_flash_current_20260911.bin`
- SHA-256: `9281D374CA27A3F7610765BC0E1C65E6D931D23B1442DE4B2E9D3D8D9C27472E`
- 9월 10일 백업과 47,243바이트가 다르고, 첫 차이는 오프셋 `0x4`, 마지막 차이는
  `0xD1EB`이다. Reset 벡터도 `0x08004A15`에서 `0x08004AC1`로 바뀌었다.
- 저장소의 STM UART 후보와도 바이너리가 일치하지 않는다. 다른 팀이 다시 빌드해
  적용한 별도 펌웨어로 판단한다.
- COM13에서 확인한 실제 문장:

```text
L=0 R=0 cap=0/0 glt=0/0 dsy=0/0 tps=896 pct=0 idle=897 can=14369/0/00000000 imu=12859/0/282887/0
```

`dsy`, `can`, `imu` 뒤 숫자는 의미가 확인되지 않은 진단 카운터로만 취급한다. 이 문장에는
Yaw rate, 횡/종가속도와 TQV 내부 연산값이 없으므로 이를 실제 0으로 해석하지 않는다.
ESP 파서는 `glt`와 `tps` 사이에 새 필드가 삽입돼도 기본 RPM/TPS를 읽도록 변경했고,
위 진단 숫자는 이름을 단정하지 않은 `stm_*_diag_*` 필드로 전달한다. 실제 센서값과
TQV 값은 STM 문장에 해당 값을 추가하기 전까지 명시적으로 미수신 상태를 유지한다.

## 2026-09-11 양방향 후보 구현

다른 팀이 설치한 바이너리는 그대로 백업해 두었고 덮어쓰지 않았다. 원본 C 소스를
바이너리에서 복구할 수 없으므로, 검증 가능한 고정 커밋 `ee9d295...` 기반 EV 오버레이에
다음 기능을 추가했다.

- PA9 → GPIO18: RPM/TPS, IMU, 출력과 TQV 내부 상태를 5Hz 텍스트로 송신.
- GPIO17 → PA10: CRC-8이 포함된 9바이트 TQV 강도 명령을 10Hz로 수신.
- 강도와 최대값은 0~100%, 5% 단위만 허용하며 알 수 없는 flag와 손상된 CRC를 거부.
- 유효 명령 시간은 500ms. ESP 명령이 끊기면 기존 Front/CAN 설정 입력으로 복귀.
- 기존 강도 변화율, 피트 최대값, 물리 TV 스위치와 모든 Rear 안전 조건을 그대로 적용.
- `torque_vectoring.c/.h`의 계산식과 `TV_Update()`는 수정하지 않음.

송신 필드는 `vehicle_speed`, `desired_yaw`, `yaw_error`, `delta_power`,
`power_left`, `power_right`, `tv_active`, `ed_active`, `traction_scale` 전부를 포함한다.
STM 후보 ARM 빌드는 성공했다(text 40,284 / data 160 / bss 7,848바이트).
ESP 빌드와 호스트 테스트도 통과했지만, 이 후보는 STM에 아직 플래시하지 않았고
PA9/PA10 실배선 왕복 및 차량 출력 검증도 수행하지 않았다.

현재 ESP USB COM8이 보이지 않아 이 호환 파서의 보드 업로드와 STM→ESP 실수신 검증은
아직 수행하지 않았다. 현재 보드 펌웨어의 출력은 ST-LINK VCP COM13에서 확인됐으므로,
ESP 입력선이 같은 TX 핀을 보고 있는지도 함께 확인해야 한다.
