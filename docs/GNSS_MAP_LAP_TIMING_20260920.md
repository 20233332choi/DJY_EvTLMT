## 구글 지도·티맵에서 참고할 원리

구글의 Location Accuracy는 GPS, Wi-Fi, 이동통신 기지국과 가속도계·자이로 등 사용 가능한 센서 정보를 이용한다. iPhone 위치 서비스도 GPS·Wi-Fi·Bluetooth·기지국을 이용할 수 있다. 웹의 Geolocation API는 기기가 추정한 WGS84 위치·정확도·측정 시각을 반환하며, 위성 GNSS 단독 출력이라고 단정할 수 없다. `enableHighAccuracy`는 높은 정확도를 요청하는 옵션이지 특정 샘플 주기나 정확도를 보장하는 옵션이 아니다.

Google Roads의 맵 매칭은 연속 위치를 도로망에 맞추는 방식이다. TMAP도 GPS 및 링크 기반 이동 궤적 서비스를 공개하지만, 공개 자료만으로 실제 앱의 내부 융합 알고리즘까지 동일하다고 단정하지 않는다. 경기장에서는 도로망에 강제로 붙이면 도로 밖 주행과 코너 궤적이 왜곡될 수 있으므로 적용하지 않았다.

휴대폰을 8자로 돌리는 동작은 나침반 방향 보정이다. GPS 절대 좌표의 오차를 없애는 보정과 구분한다.

## 보정 방법과 한계

1. 하늘이 잘 보이는 알려진 기준점에 차량과 휴대폰을 정지시킨다. 브라우저의 정확한 위치 권한과 휴대폰의 위치 정확도 개선을 켠다.
2. 피트 PC `/map`에서 **정지 상태 30초 수집**을 누른다. 최근 수집 구간에서 20점 이상·30초 이상, 정확도 10 m 이하, 측정 공백 3초 이하인 위치가 필요하다.
3. 중앙값 좌표 주변의 95% 산포가 5 m 이하이고 시작·끝 좌표 중앙값 변화가 2 m 이하인지 확인한다. 속도가 제공되면 2 km/h 이하 조건도 적용한다. 속도 미제공 기기에서는 좌표 안정성을 검사하므로 사용자가 실제 정지 상태를 유지해야 한다.
4. 측량된 기준 위경도를 입력하거나 지도에서 실제 정지 위치를 선택하고 **기준점 차이 적용**을 누른다. 지도 클릭은 시각적 정렬이며 측량 정확도를 보장하지 않는다.
5. 원본 좌표와 보정 좌표를 비교한다. 수신 정확도 수치는 임의로 낮추지 않는다. 100 m를 넘는 보정은 거절하며 같은 휴대폰에 최대 24시간만 적용한다. 장소·장착 위치·수신 환경이 바뀌면 재확인한다.

정지 평균만으로 절대 위치 오차를 알아낼 수는 없다. 기준 좌표가 있어야 일정한 위치 편차를 추정할 수 있고, 이 보정으로 시간에 따라 변하는 다중경로 오차까지 제거하지는 못한다. 수집은 45초 구간까지 사용하며 적용 시 최신 수집값이 15초 이내여야 한다.

## 랩 판정

- 피트 PC 지도에서 출발선 양 끝을 지정한다. 선 길이는 5~200 m이다. 노란 화살표가 주행 방향을 향하도록 필요시 방향을 뒤집고 저장한다.
- 기본 최소 랩 시간은 10초, 최소 주행 거리는 50 m이며 코스에 맞게 설정한다.
- 정확도 10 m 이하, 측정 시각이 포함된 최근 GPS가 있어야 측정을 시작한다. 처음 정방향으로 통과하면 랩을 시작하고 다음 정상 통과에서 완료한다.
- 출발선의 무한 연장선이 아닌 양 끝 사이를 통과해야 한다. 시작선 이전에 정확도 또는 5 m 이상 떨어져 있어야 재무장한다. 선을 가로지르는 속도는 1.5 m/s 이상이어야 하며, GPS 속도가 제공되면 3 km/h 미만은 거절한다.
- 교차 시각은 이전/현재 GPS **측정 시각**을 위치 교차 비율로 보간한다. HTTP 도착 시각은 랩 시간에 사용하지 않는다.
- 정확도 부족, 위치 튐, 3초를 넘는 측정 공백·수신 지연, 소스 재시작·교체·보정 변경은 현재 랩의 연속성을 끊는다. 이후 첫 정상 통과부터 다시 시작한다. 너무 짧은 랩 통과도 현재 랩을 무효화한다.
- 중복·역순 시각과 다른 휴대폰의 실행 중 입력을 거절한다. 측정 시각이 없는 기존 클라이언트는 지도에 표시할 수 있으나 랩 판정에는 쓰지 않는다.
- 화면의 오차 추정은 `정확도 / 출발선 수직 통과 속도 + 샘플 간격 / 2`를 각 교차점에 적용해 시작·종료분을 합친 대략적 오차 규모다. 엄밀한 신뢰구간이나 계측기 정확도 보증이 아니다.
- 예를 들어 10 m/s로 출발선을 통과하고 위치 오차가 3 m이면 위치 오차만으로 한 교차점에 약 0.3초 규모의 시간 오차가 생길 수 있다. 인터넷 지연 제거와 위치 정확도 향상은 서로 다른 문제다.

## 데이터와 UI

- `/map`: 실제 OpenStreetMap 위 원본/보정 궤적, 정확도 원, 진행 방향, 추적/전체 보기, 기준점 보정, 출발선, 현재/직전/최고 랩, 과거 기록 및 CSV.
- `/pit`: 기존 빈 배경 궤적 대신 지도 미리보기와 전체 GPS 화면 링크.
- `/phone`: OS 위치 샘플의 측정 시각과 휴대폰/송신 세션 ID를 전송한다. 기존 800 ms 샘플 버리기를 제거하고 최대 10개씩 순서대로 묶는다. 단일 진행 요청, 100점 대기열, 초과·전송 실패 카운터를 제공한다. 위치 제공 주기 자체를 높이거나 네트워크 실패를 무손실로 복구하는 구현은 아니다.
- 좌표 부드럽게 보이기용 예측, 도로 강제 정렬, IMU 기반 위치 추측은 랩 판정에 사용하지 않는다.
- 원본·보정 좌표, GPS 측정 시각, 서버 수신 시각, 정확도, 거절 이유, 보정 ID를 보존한다.
- 랩 측정을 시작하면 기존 텔레메트리 DB의 `gnss_runs`, `gnss_fixes`, `gnss_laps`에 자동 저장한다. 일반 TV/BMS 기록은 피트 화면에서 별도로 시작한다. `gnss_settings`에는 출발선과 보정을 저장한다.
- 과거 GPS는 1,000점씩 고정된 끝 커서로 페이지 조회하며 CSV는 표시 페이지를 내보낸다. 랩 CSV는 해당 측정의 완료 랩을 내보낸다.
- 재시작 시 진행 중이던 GPS 측정은 `INTERRUPTED`로 보존하고 자동 재시작하지 않는다. 과거 랩은 기록에서 조회한다.
- 외부 지도·기록 조회는 가능하고 출발선·보정·측정 시작/종료는 기존 정책대로 피트 PC만 가능하다.

지도 타일은 브라우저에서 OpenStreetMap에 직접 요청한다. 출처 표시를 유지하고 타일 캐시는 브라우저 정책을 사용하며 오프라인 대량 다운로드는 하지 않는다. 자동 UI 테스트에는 가짜 타일을 사용한다. 타일 연결 실패 시 좌표 표시와 랩 판정은 유지한다.

## 다음 단계: 차량 센서 융합

현재는 휴대폰 OS가 제공하는 위치를 사용한다. 차량 IMU와 RPM까지 융합하려면 휴대폰 GPS 시각을 차량 기준 시각으로 변환하는 오프셋·드리프트 추정과 GNSS 안테나/휴대폰 장착 위치를 먼저 검증해야 한다. 그 다음 위치·속도·방향·자이로 바이어스를 상태로 두는 필터를 검토한다.

확인된 차량 좌표는 +X 전방, +Y 좌측, +Z 위다. 따라서 IMU +Z yaw 회전은 좌회전이고, 북쪽 기준 시계 방향으로 증가하는 지도 heading의 변화율은 `-gyro_z` 관계를 가진다. 좌우 RPM 환산 속도는 슬립 시 신뢰도를 낮춰야 한다. 이런 검증 없이 GPS 사이를 IMU로 채워 넣어 계측 정확도가 좋아졌다고 표시하지 않는다.
