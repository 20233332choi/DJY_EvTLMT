## 시간 기준과 CAN 프로토콜

후방 TIM5의 단조 증가 카운터를 차량 기준 시간으로 사용한다. 각 보드는 TIM5를 명목상 1 MHz로 동작시키고 32비트 오버플로를 64비트로 확장한다. UTC, Windows 시각, ESP 수신 시각과는 별개다. HSI 기반이므로 표의 마이크로초는 후방 발진기 기준 단위이며 절대 시간 정확도를 인증한 값이 아니다.

| CAN ID | 방향 | 내용 |
|---|---|---|
| 0x080 | 후방 → 전방 | 요청 cookie32, 후방 송신 직전 t1 |
| 0x081 | 전방 → 후방 | cookie32, 전방 수신 ISR 시각 t2 |
| 0x082 | 전방 → 후방 | cookie32, 전방 응답 enqueue 직전 t3; 후방은 수신 t4 기록 |
| 0x100 | 전방 → 후방 | SAS16, TPS16, flags8, seq16, 버전 marker 0xA1 |
| 0x101 | 전방 → 후방 | seq16, 전방 취득 중간 시각32, 취득 구간 길이16 |

모든 프레임은 표준 ID, DLC 8, little endian이다. 기존 0x100 레거시 센서 데이터도 후방에서 받지만 시간 동기화 측정 대상으로 인정하지 않는다. 0x100/0x101은 동일 sequence이고 5 ms 이내 수신된 경우만 묶는다. 조향과 TPS는 순차 취득하므로 중간 시각과 전체 취득 구간을 함께 기록한다.

전방 v2 센서 데이터가 최근 500 ms 이내 들어왔을 때만 후방이 100 ms 간격으로 동기화 요청을 보낸다. 전방이 없는 단독 계측 구성에서는 요청을 보내지 않는다. 이는 초기 실측에서 전방 없는 CAN에 요청을 보내 오류가 누적된 문제를 보완한 것이다.

최근 최대 24개 왕복 교환으로 `rear = rate × front + offset`을 추정한다. 최소 8개 표본 및 500 ms 구간이 필요하다. RTT 2 ms 초과, 교환 만료, cookie 불일치, 큰 시계 불연속을 거른다. 시계 불연속 시 재취득하며 500 ms 갱신 중단 시 매핑을 무효화한다. 32비트 wrap은 제한된 시간 차분으로 처리한다. 별도의 영구 boot ID를 교환하는 방식은 아니다.

회귀 잔차, 최대 반 RTT, 소프트웨어 여유 및 외삽 여유로 오차 추정치를 계산하고 1 ms 이하일 때만 유효로 표시한다. CAN 하드웨어 SOF 타임스탬프가 아니므로 이 수치는 **추정치이며 보장 오차가 아니다**. 실제 버스 부하와 양방향 비대칭 지연은 전방 연결 후 검증해야 한다.

구현: 양쪽 `vehicle_clock.c`, `board_time_sync.c`, `time_sync_model.h`; 후방 `sensor_time_pair.h`, `can_comm.c`; 전방 센서 취득 ISR.

## 후방 계측 방법

`imu_sensor.c`에서 UART4 IDLE 인터럽트 시각과 DMA 위치를 기록한다. 115200 baud, 8N1 전송 시간을 이용해 각 패킷 마지막 바이트 도착 시각을 역산한다. 이후 메인 루프의 파싱 시각과 TIM6 제어 ISR 시작 시각을 같은 TIM5 시계로 비교한다. IDLE IRQ 서비스 지연과 전송 버스트의 바이트 간 간격은 이 추정의 오차 요인이다.

100 Hz 제어 틱마다 입력 나이와 실행 시간을 집계하고, 각 유효 gyro 패킷마다 도착 간격과 파싱 지연을 집계한다. 모든 이벤트를 누적 통계에 반영하지만 개별 100 Hz 원시 표본을 USB로 보내는 방식은 아니다. USB의 `#TIME` 출력은 기존 상태 출력 주기마다 한 지표씩 비동기로 전송한다. 계측 자체는 대시보드 갱신 주기에 의존하지 않는다. ESP/대시보드에는 이번 `#TIME` 필드를 추가하지 않았다.

부팅/보정 후 제어 타이머 시작부터 1초 동안 입력 시각만 추적하여 초기 DMA 적체가 빠지게 한 뒤 통계를 시작한다. P95는 히스토그램 버킷의 상한이며 정확한 분위수가 아니다. 특히 10 ms 근처 주기에서 `p95_upper_us=20000`이어도 실제 최대값이 약 10.006 ms일 수 있다.

제어 주기 최솟값 9.995 ms, 10 ms 이상 실행 시간 초과 0회. 전방 동기화 `sync=0`, 유효 교환 0개, 전방/RPM 지연 표본 0개이므로 해당 값은 미측정이다. 0 ms 지연을 뜻하지 않는다. 정상 주행의 TV 실행 경로를 검증한 결과도 아니다.

최종 수집 구간 내 CAN 수신 0, CAN 오류 0, 후방 UART 오류 0이었다. 전방 입력 부재로 `fault=1`, TV/ED 비활성 상태가 유지되었다. 계측 후 ESP 인터넷 릴레이에서 STM/IMU 온라인을 확인했다. 전체 진단 행의 첫/끝 후방 시각 차이는 약 54.000초이다.

이전 `timing-rear-baseline.json`은 부팅 통계가 포함되며, `timing-rear-steady.json`은 전방 없는 CAN 요청 억제 전 결과다. 최종 판정에는 위 final 파일을 사용한다. 최초 `timing-rear-initial.json`은 nano printf의 64비트 포맷 지원 문제로 정상 진단 행을 얻지 못한 실패 기록이다.

## 원인 분석 및 해석

후방 `main.c` 메인 루프에서 `IMU_ProcessData()`를 수행하지만 `Telemetry_Publish()` 안의 `HAL_UART_Transmit(&huart2, ..., 80)`가 USB 상태 문장의 전송 완료를 기다린다. 이 동안 제어 ISR은 계속 실행되고 DMA도 계속 수신하지만 새 IMU 패킷의 파싱은 늦어진다. 따라서 제어 주기 10 ms 유지와 최신 IMU 값 사용은 별개다.

전방 없는 구성에서 상태 문장 길이는 약 330바이트이다. 115200 baud 8N1에서는 전송에 약 29 ms가 필요하여 관측된 수십 ms 지연을 설명하는 직접적인 블로킹 경로다. 모든 지연을 이 경로에만 귀속시키는 A/B 검증은 하지 않았으며 SD flush 등 다른 메인 루프 작업도 영향을 줄 수 있다. 앞선 전방 레거시 데이터가 수신되던 계측에서는 더 긴 상태 문장과 최대 약 42 ms의 gyro 입력 나이가 관측되었다. 서로 다른 운전 조건의 결과를 같은 시험으로 합치지 않는다.

후속 개선 우선순위는 기존 USB 상태 출력도 큐와 IT/DMA로 처리하여 메인 루프를 막지 않게 하는 것이다. 그 뒤 같은 계측으로 지연 감소와 데이터 누락 여부를 비교하고 SD flush의 최악 지연도 확인해야 한다. 이번 단계에서는 해당 블로킹 출력과 PID 게인을 변경하지 않았다.

이 계측은 **UART 수신 이후 입력 나이**이다. IMU 내부 측정·디지털 필터 지연, 후방 `IMU_UpdateFilter()`의 deglitch/LPF 위상 지연, 구동계 응답은 별도다. 따라서 측정값을 전체 물리 yaw → 토크 응답 지연으로 해석하면 안 된다. 3~4개 제어 주기만큼 오래된 입력이 사용되므로 현재 결과만으로 PID 튜닝에 충분히 작은 지연이라고 승인할 수 없다. 정지 상태에서는 TV 제어가 비활성이고 RPM 입력이 없으므로 주행 중 폐루프 안정성 또는 활성 PID 최악 실행 시간도 검증하지 못한다.
